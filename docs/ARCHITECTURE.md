# ระบบบริหารจัดเก็บเงินบำรุงการศึกษา โรงเรียนวัดเสาหิน จังหวัดเชียงใหม่

## เอกสารสถาปัตยกรรม โครงสร้างข้อมูล และความปลอดภัย (ฉบับใช้พัฒนา)

| รายการ | รายละเอียด |
|---|---|
| สถานะ | v0.4 ระยะที่ 1–4 เสร็จแล้ว (โครงสร้างฐานข้อมูล, ระบบเข้าสู่ระบบและสิทธิ์, ระบบนักเรียน, ระบบเรียกเก็บและรับชำระ) |
| วันที่ | 21 พฤศจิกายน 2569 (ร่างแรก 20 พฤศจิกายน 2569) |
| ขอบเขต | เงินบำรุงการศึกษาเท่านั้น |

> **หลักการสำคัญ:** ระบบนี้เป็น **ทะเบียนคุมและบันทึกอ้างอิง** ของใบเสร็จรับเงินจากเล่มจริงของทางราชการ
> ระบบ **ไม่ออกใบเสร็จอิเล็กทรอนิกส์** และ **ไม่สร้างเลขใบเสร็จขึ้นเอง** ทุกเลขที่ในระบบต้องมาจากเล่มจริงที่ลงทะเบียนไว้แล้ว

## 1. หลักการออกแบบ

1. **ข้อมูลการเงินแบบเพิ่มต่อท้ายเท่านั้น (append-only)**
   ระบบไม่ลบและไม่เขียนทับจำนวนเงินที่บันทึกแล้ว เมื่อต้องแก้ไข ระบบจะสร้างรายการยกเลิกหรือรายการแก้ไขใหม่ที่อ้างถึงรายการเดิม รายการเดิมยังอยู่ให้ตรวจสอบย้อนหลังได้
2. **ระบบคำนวณยอดคงเหลือจากข้อมูลต้นทางทุกครั้ง**
   ชีตไม่เก็บช่อง "ยอดคงเหลือ" ไว้ ระบบรวมยอดจากรายการเรียกเก็บ รายการลดหย่อน และรายการชำระทุกครั้งที่แสดงผล ยอดคงเหลือจึงตรงกับประวัติเสมอ
3. **ตรวจสิทธิ์ที่ฝั่ง Server ทุกคำขอ และปฏิเสธเป็นค่าเริ่มต้น (default deny)**
   การซ่อนปุ่มบนหน้าเว็บเป็นเพียงความสะดวกในการใช้งาน ไม่ใช่การควบคุมสิทธิ์
4. **ทุกการบันทึกทำภายใต้ LockService**
   ระบบตรวจข้อมูลซ้ำอีกครั้งหลังได้ lock แล้ว จึงค่อยเขียน
5. **เรียบง่ายและดูแลต่อได้**
   ไม่มีบริการเสียเงิน ไม่มีฐานข้อมูลภายนอก โค้ดแยกไฟล์ตามหน้าที่ ตั้งชื่อชัดเจน และมีคำอธิบายภาษาไทย

### 2.1 ส่วนประกอบ

| ส่วน | เทคโนโลยี | หน้าที่ |
|---|---|---|
| Frontend | HtmlService, HTML/CSS/JS ล้วน | หน้าจอทั้งหมด, router ฝั่งหน้าเว็บ, ตาราง, ฟอร์ม, หน้าพิมพ์ |
| API | ฟังก์ชัน `api(request)` ฟังก์ชันเดียว | ตรวจ session, ตรวจสิทธิ์, ตรวจข้อมูล, เรียก service |
| Services | ไฟล์ `.gs` แยกตามโมดูล | กฎทางธุรกิจ เช่น เรียกเก็บ รับชำระ ใบเสร็จ ยอดค้าง |
| Repository | `Db.gs` | อ่านและเขียนชีตโดยอ้างชื่อคอลัมน์จากหัวตาราง ไม่อ้างเลขคอลัมน์ |
| Database | Google Sheets | 15 ชีต (12 ชีตตามข้อกำหนด และเพิ่ม 3 ชีต ดูหัวข้อ 5) |
| Secrets | Script Properties | รหัส Spreadsheet, pepper ของรหัสผ่าน, โฟลเดอร์สำรอง |
| Session | CacheService (ScriptCache) | token พร้อมเวลาหมดอายุ, ตัวนับการ login ผิด |
| Backup | DriveApp + Time-driven trigger | คัดลอก Spreadsheet ทั้งไฟล์ทุกวัน |

### 2.2 ข้อตัดสินใจหลัก

- **ใช้สคริปต์แบบผูกกับ Spreadsheet (container-bound) ที่โรงเรียนสร้างไว้แล้ว**
  ติดตั้งง่าย และเพิ่มเมนูติดตั้งในชีตได้ ระบบเก็บรหัส Spreadsheet ไว้ใน Script Properties (`DB_SPREADSHEET_ID`) เพื่อให้สลับไปใช้ไฟล์สำรองตอนกู้คืนได้ ค่าเริ่มต้นคือไฟล์ที่ผูกอยู่
- **API มีทางเข้าเดียว**
  ใน Apps Script ทุกฟังก์ชันที่ชื่อไม่ลงท้ายด้วย `_` ถูกเรียกจากเบราว์เซอร์ผ่าน `google.script.run` ได้ ระบบจึงเปิดเผยเพียง `doGet`, `api` และฟังก์ชันติดตั้งที่ตรวจว่าผู้เรียกเป็นเจ้าของ ฟังก์ชันอื่นทั้งหมดลงท้ายด้วย `_`
- **ไม่ใช้ไลบรารีภายนอก**
  กราฟเขียนด้วย HTML/CSS/SVG เอง จึงพิมพ์ได้ดีและไม่พึ่ง CDN ฟอนต์ Sarabun โหลดจาก Google Fonts และใช้ฟอนต์ระบบแทนเมื่อโหลดไม่ได้ การอ่านไฟล์ .xlsx ใช้โค้ดของระบบเอง (แตกไฟล์ด้วย `DecompressionStream` ของเบราว์เซอร์ แล้วอ่าน XML ของ Excel) ไฟล์ไม่ถูกส่งไปที่อื่น มีเพียงข้อมูลตารางที่อ่านได้ถูกส่งให้ Server ตรวจสอบ ส่วน CSV และการคัดลอกวางจาก Excel ใช้ได้ทุกเบราว์เซอร์
- **พิมพ์และบันทึกเป็น PDF ผ่านคำสั่งพิมพ์ของเบราว์เซอร์**
  ตัวแปลง PDF ฝั่ง Apps Script แสดงฟอนต์ไทยได้ไม่สมบูรณ์ การพิมพ์ผ่านเบราว์เซอร์ด้วย CSS `@media print` จึงแม่นยำกว่า

## 3. การเผยแพร่และการยืนยันตัวตน

### 3.1 ข้อเท็จจริงทางเทคนิคที่ต้องรู้

- ถ้าตั้ง **Execute as: User accessing the web app** สคริปต์จะทำงานด้วยสิทธิ์ของผู้ใช้แต่ละคน ผู้ใช้ทุกคนจึงต้องมีสิทธิ์แก้ไข Spreadsheet และ**เปิดชีตแก้ตัวเลขได้โดยตรง** ข้ามการตรวจสิทธิ์และ Audit Log ทั้งหมด → **ไม่ใช้รูปแบบนี้**
- ถ้าตั้ง **Execute as: Me** (เจ้าของ) Spreadsheet ไม่ต้องแชร์ให้ใครเลย ข้อมูลเข้าถึงได้ผ่านแอปเท่านั้น แต่ `Session.getActiveUser().getEmail()` จะ**คืนค่าว่าง** ถ้าผู้ใช้กับเจ้าของสคริปต์ไม่ได้อยู่ใน Google Workspace โดเมนเดียวกัน (เช่น ทั้งคู่ใช้ @gmail.com ส่วนตัว)

### 3.2 ทางเลือก

| ทางเลือก | การตั้งค่า | ใช้ได้เมื่อ | ความปลอดภัย | ข้อเสีย |
|---|---|---|---|---|
| **A. บัญชี Google ของโรงเรียน** | Execute as Me + Anyone within โดเมน | เจ้าของระบบและผู้ใช้ทุกคนมีบัญชีในโดเมน Google Workspace เดียวกัน | สูงสุด: Google ยืนยันตัวตน รองรับ 2-Step Verification ระบบไม่ต้องเก็บรหัสผ่าน | ต้องมีโดเมน Workspace |
| **B. ชื่อผู้ใช้และรหัสผ่านของระบบ** | Execute as Me + Anyone with Google account (หรือ Anyone) | ใช้ได้ทุกกรณี รวมถึงบัญชี Gmail ส่วนตัว | ปานกลางถึงดี ถ้าทำตามข้อ 3.4 | ระบบต้องดูแลรหัสผ่านเอง ดูข้อจำกัดในข้อ 3.5 |
| C. Execute as User accessing | — | — | **ไม่ผ่าน** ผู้ใช้แก้ชีตได้ตรง | ไม่แนะนำ |

### 3.3 ข้อเสนอ

- ถ้าโรงเรียนมี Google Workspace โดเมนเดียวกันสำหรับทุกคน **ใช้ทางเลือก A**
- ถ้าไม่มี **ใช้ทางเลือก B** และตั้ง "Anyone with Google account" เป็นอีกชั้นหนึ่ง: ผู้เข้าเว็บต้องลงชื่อเข้าใช้ Google ก่อน แม้ระบบจะไม่ได้ใช้อีเมลนั้นยืนยันตัวตน ก็ช่วยลดการเข้าถึงหน้า login จากผู้ไม่ระบุตัวตนได้
- ระบบรองรับทั้งสองโหมดผ่านค่า `AUTH_MODE` ใน Script Properties (`PASSWORD` หรือ `GOOGLE`) ค่านี้เปลี่ยนจากหน้าเว็บไม่ได้ ต้องให้เจ้าของระบบเปลี่ยนในโปรแกรมแก้ไขสคริปต์เท่านั้น
- ทั้งสองโหมด **ไม่แชร์ Spreadsheet และโปรเจกต์สคริปต์ให้ผู้ใช้คนใด**
- **บัญชีเจ้าของระบบควรเป็นบัญชีกลางของโรงเรียน ไม่ใช่บัญชีส่วนตัวของครู**
  เพื่อไม่ให้ข้อมูลติดตัวบุคคลเมื่อย้ายหรือเกษียณ ต้องเปิด 2-Step Verification และให้ผู้มีอำนาจของโรงเรียนกำหนดผู้ถือรหัสผ่าน

### 3.4 รายละเอียดโหมดรหัสผ่าน (B)

| เรื่อง | วิธีการ |
|---|---|
| การเก็บรหัสผ่าน | เก็บเฉพาะค่าแฮช: salt สุ่มต่อผู้ใช้ + pepper ลับใน Script Properties + HMAC-SHA256 วนซ้ำ (ระบบวัดความเร็วเครื่อง Google ตอนติดตั้งแล้วเลือก 300–5,000 รอบ ให้ใช้เวลาราว 0.25 วินาที และแฮชใหม่อัตโนมัติเมื่อเพิ่มจำนวนรอบ) รูปแบบ `v1$รอบ$salt$hash` เพื่ออัปเกรดวิธีภายหลังได้ |
| Session | token สุ่มอย่างน้อย 244 บิต (`Utilities.getUuid()` 2 ชุด) ใน CacheService เก็บเป็นค่าแฮชของ token ไม่ใช่ token ตรง ๆ |
| หมดอายุ | ไม่ใช้งาน 30 นาทีหมดอายุ (ตั้งค่าได้) และอายุสูงสุด 8 ชั่วโมง |
| ยกเลิก session ทันที | เมื่อปิดบัญชี รีเซ็ตรหัส หรือเปลี่ยนบทบาท ระบบเพิ่ม `SessionVersion` ของผู้ใช้ ทุก session เดิมของคนนั้นใช้ไม่ได้ทันที |
| ตรวจสถานะทุกคำขอ | ทุกคำขออ่านสถานะและบทบาทล่าสุดจากชีต Users ไม่เชื่อค่าที่หน้าเว็บส่งมา |
| ป้องกันการเดารหัส | login ผิด 5 ครั้งใน 15 นาที ระบบล็อกชื่อผู้ใช้นั้น 15 นาที ข้อความแจ้งเตือนเหมือนกันทุกกรณี ("ชื่อผู้ใช้หรือรหัสผ่านไม่ถูกต้อง") เพื่อไม่ให้รู้ว่าชื่อผู้ใช้ใดมีอยู่ |
| นโยบายรหัสผ่าน | อย่างน้อย 8 ตัวอักษร บังคับเปลี่ยนเมื่อเข้าครั้งแรก และหลังผู้ดูแลระบบรีเซ็ต |
| ผู้ดูแลระบบคนแรก | สร้างจากเมนูในชีต ซึ่งมีเพียงเจ้าของไฟล์ที่เปิดได้ ไม่มีหน้า "สมัคร" บนเว็บ |
| Log | ไม่บันทึกรหัสผ่าน ค่าแฮช หรือ token ลง Log, AuditLog หรือข้อความแสดงข้อผิดพลาด |

### 3.5 ข้อจำกัดของโหมด B ที่ต้องยอมรับก่อนใช้งานจริง

1. **ไม่มีอัลกอริทึม bcrypt หรือ Argon2 ใน Apps Script**
   ระบบใช้ HMAC-SHA256 วนซ้ำแทน ซึ่งแข็งแรงน้อยกว่า ความเสี่ยงจะเกิดก็ต่อเมื่อชีต Users รั่วไหล
2. **Apps Script ไม่ให้ IP ของผู้ใช้**
   ระบบจำกัดการเดารหัสได้ตามชื่อผู้ใช้เท่านั้น จำกัดตามเครื่องไม่ได้
3. **ไม่มีการรีเซ็ตรหัสผ่านทางอีเมล**
   ผู้ดูแลระบบเป็นผู้รีเซ็ตให้ ข้อดีคือลดช่องโหว่
4. **CacheService อาจล้างข้อมูลก่อนเวลา**
   ผู้ใช้อาจต้อง login ใหม่โดยไม่คาดคิด ข้อมูลไม่สูญหาย
5. **token อยู่ใน sessionStorage**
   ถ้ามีช่องโหว่ XSS ผู้โจมตีอาจขโมย token ได้ ระบบจึงแสดงข้อมูลผ่าน `textContent` หรือ escape ทุกจุด (ดูหัวข้อ 10)

### 4.2 การบังคับใช้สิทธิ์ที่ฝั่ง Server

ทุกคำขอผ่านฟังก์ชันเดียว และสิทธิ์ของทุก action อยู่ในตารางเดียว ตรวจทานได้ในที่เดียว:

```js
// Config.gs: action ที่ไม่อยู่ในตารางนี้ถูกปฏิเสธเสมอ
const ACTIONS = {
  'students.search':  { roles: ['FINANCE', 'DIRECTOR'],  write: false },
  'payments.create':  { roles: ['FINANCE'],              write: true  },
  'approvals.decide': { roles: ['DIRECTOR'],             write: true  },
  'users.create':     { roles: ['ADMIN'],                write: true  },
  // ...
};

// Api.gs: ทางเข้าเดียวจากหน้าเว็บ
function api(request) {
  try {
    const def = ACTIONS[request && request.action];
    if (!def) throw appError_('FORBIDDEN');
    const user = authenticate_(request.token);       // ตรวจ session ทุกครั้ง
    authorize_(user, def.roles);                      // ตรวจบทบาทล่าสุดจากชีต Users
    const input = validate_(request.action, request.payload);
    const run = () => HANDLERS_[request.action](user, input);
    return ok_(def.write ? withLock_(run) : run());
  } catch (e) {
    return fail_(e);   // ส่งเฉพาะข้อความที่ปลอดภัย ไม่ส่ง stack trace
  }
}
```

### 5.1 หลักทั่วไป

| เรื่อง | วิธีการ |
|---|---|
| รหัสอ้างอิง | ทุกชีตมีคอลัมน์แรกเป็นรหัสเฉพาะ ไม่ใช้เลขแถว รูปแบบ `คำนำหน้า-ปปปปดดววชชนนวว-XXXXXX` (ค.ศ. เวลาไทย + ฐานสิบหกสุ่ม 6 ตัว) เช่น `PAY-20261121143015-A7F3C2` อ่านง่าย เรียงตามเวลา และระบบตรวจไม่ให้ซ้ำภายใต้ lock |
| หัวตาราง | แถวที่ 1 เป็นชื่อคอลัมน์ภาษาอังกฤษ (ใช้เป็นคีย์ในโค้ด) มีหมายเหตุภาษาไทยบนหัวคอลัมน์ ตรึงแถวแรกไว้ โค้ดอ้างคอลัมน์ด้วยชื่อ จึงเพิ่มคอลัมน์ใหม่ต่อท้ายได้โดยโค้ดเดิมไม่พัง |
| จำนวนเงิน | เก็บเป็นตัวเลข ทศนิยม 2 ตำแหน่ง โค้ดคำนวณเป็น **สตางค์ (จำนวนเต็ม)** เพื่อตัดปัญหาทศนิยมคลาดเคลื่อน แสดงผล `1,000.00 บาท` และมีจำนวนเงินเป็นตัวอักษรไทย (เช่น "หนึ่งพันบาทถ้วน") สำหรับเอกสาร |

| ข้อความ | คอลัมน์ข้อความตั้งรูปแบบเป็น Plain text ข้อความที่ขึ้นต้นด้วย `=` `+` `-` `@` ถูกนำหน้าด้วย `'` เพื่อกัน formula injection จากไฟล์นำเข้า |

| คอลัมน์มาตรฐาน | ทุกชีตยกเว้น AuditLogs มี `CreatedAt, CreatedBy, UpdatedAt, UpdatedBy` ระบบบันทึกเองเสมอ (`UpdatedAt` ว่าง = ยังไม่เคยแก้ไข) และใช้ `CreatedBy/CreatedAt` เป็นผู้ขอและเวลาที่ขอในชีตคำขอ |

## 6. กฎทางธุรกิจหลัก

### 6.1 สูตรยอดเงินและสถานะ (ต่อรายการเรียกเก็บ)

```
ยอดเรียกเก็บสุทธิ = GrossAmount − Σ FeeAdjustments (Status = ACTIVE)
ยอดชำระสะสม     = Σ PaymentAllocations (ACTIVE) ที่ Payment ยัง ACTIVE
ยอดคงเหลือ       = ยอดเรียกเก็บสุทธิ − ยอดชำระสะสม
```

ระบบกำหนดสถานะตามลำดับ:

| ลำดับ | เงื่อนไข | สถานะ |
|---|---|---|
| 1 | รายการถูกยกเลิก (Status = CANCELLED) | ยกเลิก |
| 2 | ยอดสุทธิ = 0 เพราะได้รับยกเว้นหรือลดหย่อนเต็มจำนวน | ได้รับยกเว้น |
| 3 | ยอดชำระสะสม = 0 | ยังไม่ชำระ |
| 4 | ยอดชำระสะสมน้อยกว่ายอดสุทธิ | ชำระบางส่วน |
| 5 | ยอดชำระสะสมเท่ากับยอดสุทธิ | ชำระครบ |

ข้อห้ามที่ระบบตรวจ:

- ห้ามตัดชำระเกินยอดคงเหลือ ระบบไม่รับเงินเกินและไม่มีเครดิตล่วงหน้า
- ห้ามลดหย่อนจนยอดสุทธิต่ำกว่ายอดที่ชำระแล้ว

### 6.2 การเรียกเก็บ

1. เจ้าหน้าที่ตั้งอัตราตามปี ภาค และระดับชั้น พร้อมวันเริ่มและวันครบกำหนด
2. กด "สร้างรายการเรียกเก็บ" ระบบแสดงตัวอย่างก่อนยืนยัน และสร้างให้นักเรียนชั้นนั้นในปีนั้นที่กำลังศึกษาหรือจบการศึกษาในปีนั้น ที่ยังไม่มีรายการของอัตรานั้น ข้ามผู้ย้ายออกและผู้ที่รายการเดิมถูกยกเลิก (ถ้าต้องเรียกเก็บ ให้เพิ่มรายบุคคล) จึงกดซ้ำได้โดยไม่เกิดรายการซ้ำ (D-27)
   - ต้องกรอกเอกสารที่อนุมัติอัตราก่อน (D-06) และชั้นเดียวกันในปีเดียวกันตั้งอัตรารายภาคเรียนซ้อนกับทั้งปีไม่ได้ (D-28)
3. สร้างรายบุคคลได้ เช่น นักเรียนย้ายเข้ากลางปี
4. หลังมีรายการเรียกเก็บแล้ว แก้จำนวนเงินและวันครบกำหนดในอัตราไม่ได้ ถ้าต้องการให้แต่ละคนจ่ายต่างกัน ใช้การลดหย่อน
5. ยกเลิกรายการเรียกเก็บได้เมื่อยังไม่มีการชำระเท่านั้น ต้องกรอกเหตุผล และขออนุมัติถ้าตั้งค่าไว้

### 6.3 การรับชำระ

1. ค้นหานักเรียน ระบบแสดงรายการค้างทุกปี (รวมหนี้ปีก่อน) และ **เลขที่ถัดไปของเล่มที่กำลังใช้**
2. เจ้าหน้าที่เขียนใบเสร็จจริง แล้วกรอก วันที่รับเงิน จำนวนเงิน ช่องทาง ผู้รับเงิน หมายเหตุ เลขเล่ม เลขที่ และการตัดชำระ ค่าเริ่มต้นคือตัดหนี้เก่าสุดก่อน ซึ่งเจ้าหน้าที่ปรับได้
3. ต้องติ๊กยืนยัน **"ข้าพเจ้าได้ตรวจสอบใบเสร็จรับเงินฉบับจริงแล้ว เลขเล่ม เลขที่ และจำนวนเงินตรงกับที่บันทึก"** ระบบปฏิเสธที่ฝั่ง Server ถ้าไม่ได้ยืนยัน
4. หน้าเว็บสร้าง `RequestKey` ใหม่ทุกครั้งที่เปิดฟอร์ม ถ้ากดบันทึกซ้ำหรือเน็ตหลุดแล้วส่งใหม่ ระบบจะไม่บันทึกซ้ำ
5. Server ทำตามลำดับ: ขอ lock → ตรวจ RequestKey → ตรวจเล่มและเลขที่ → **คำนวณยอดคงเหลือใหม่ภายใต้ lock** → ตรวจว่ายอดตัดชำระรวมเท่ากับจำนวนเงิน และไม่เกินยอดคงเหลือ → เขียน ReceiptEntries, Payments, PaymentAllocations, AuditLogs → ถ้าเล่มครบให้เปลี่ยนเป็น FULL → ปล่อย lock
6. ระบบตอบกลับ: ยอดคงเหลือใหม่ สถานะ เลขที่ถัดไป และคำเตือน (เช่น เลขขาดช่วง หรือเล่มใกล้หมด)

### 6.4 ทะเบียนคุมใบเสร็จ (ตามข้อกำหนดข้อ 8)

| # | ข้อกำหนด | วิธีการในระบบ |
|---|---|---|
| 1 | แสดงเลขที่ถัดไป | เลขที่ถัดไป = เลขต่ำสุดในช่วงของเล่ม ACTIVE ที่ยังไม่อยู่ใน ReceiptEntries |
| 2 | เลขเล่มและเลขที่ไม่ซ้ำ | เลขเล่มไม่ซ้ำทั้งระบบ และ (เล่ม + เลขที่) ไม่ซ้ำ ตรวจภายใต้ lock ทุกครั้ง |
| 3 | ใช้ครบเล่มแล้วแจ้งเตือนและหยุด | เมื่อทุกเลขถูกใช้หรือยกเลิกแล้ว ระบบเปลี่ยนเล่มเป็น FULL และปฏิเสธการบันทึกในเล่มนั้น เตือนล่วงหน้าเมื่อเหลือน้อยกว่า `RECEIPT_LOW_WARNING` |
| 4 | เปลี่ยนเล่มเมื่อลงทะเบียนเล่มใหม่แล้วเท่านั้น | เปิดใช้ (ACTIVE) ได้เฉพาะเล่มที่ลงทะเบียนแล้ว และมีเล่ม ACTIVE ได้ครั้งละ 1 เล่ม |
| 5 | ไม่สร้างเลขใบเสร็จเอง | ระบบเพียงเสนอเลขจากช่วงของเล่มจริง เจ้าหน้าที่ต้องยืนยัน ไม่มีการออกเลขนอกเล่ม |
| 6 | ตรวจใบเสร็จจริงก่อนบันทึก | บังคับติ๊กยืนยัน และตรวจที่ Server |
| 7 | เลขที่ยกเลิกเก็บประวัติ ห้ามลบหรือใช้ซ้ำ | เลขที่ยกเลิกยังอยู่ใน ReceiptEntries ตลอดไป ระหว่างรออนุมัติ เลขก็ถูกกันไว้ |
| 8 | แสดงเลขที่ยังไม่ใช้ ใช้แล้ว ยกเลิก | หน้าเล่มใบเสร็จแสดงตารางเลขทุกตัว แยกสีตามสถานะ |
| 9 | แจ้งเตือนเลขขาดช่วง | เลขที่ต่ำกว่าเลขสูงสุดที่ใช้แล้ว แต่ไม่มีรายการ ถือว่าขาดช่วง แสดงบน Dashboard จนกว่าจะบันทึกหรือยกเลิกเลขนั้น |
| 10 | กันเลขซ้ำเมื่อหลายคนบันทึกพร้อมกัน | LockService + ตรวจซ้ำหลังได้ lock คนที่ส่งทีหลังจะได้ข้อความ "เลขที่นี้ถูกบันทึกแล้ว" พร้อมเลขถัดไปใหม่ |

เรื่อง `RECEIPT_STRICT_SEQUENCE`:

- ค่าเริ่มต้น **TRUE** (ตัดสินใจ D-11): ต้องใช้เลขถัดไปเท่านั้น ถ้าจะข้ามเลขต้องยกเลิกเลขนั้นพร้อมเหตุผลก่อน จึงไม่เกิดเลขขาดช่วง
- ถ้าตั้ง **FALSE**: ใช้เลขอื่นในเล่มได้ แต่ต้องยืนยันคำเตือน และระบบแสดงเลขขาดช่วงบน Dashboard จนกว่าจะแก้

| แก้ข้อมูลนักเรียน | แก้ได้ และบันทึกค่าเดิมกับค่าใหม่ |

### 6.6 การอนุมัติ

```
เจ้าหน้าที่ยื่นคำขอ (มีเหตุผล) → ApprovalRequests: PENDING
  → ผู้อำนวยการ อนุมัติ  → ระบบดำเนินการตามคำขอ และบันทึก Audit
  → ผู้อำนวยการ ไม่อนุมัติ → ไม่มีผลกับข้อมูล และบันทึกเหตุผล
```

- ระหว่างรออนุมัติ ข้อมูลเดิมยังมีผลตามเดิม ยกเว้นเลขใบเสร็จที่ขอยกเลิก ซึ่งถูกกันไว้ไม่ให้ใช้
- ผู้อำนวยการเห็นคิวคำขอที่รอพิจารณาบน Dashboard

### 6.7 การขึ้นปีการศึกษาใหม่

1. ผู้ดูแลระบบสร้างปีการศึกษาใหม่
2. เจ้าหน้าที่ใช้เครื่องมือ "เลื่อนชั้น" ระบบสร้าง Enrollments ปีใหม่จากปีเดิม (ป.1 → ป.2 …) ชั้นสุดท้ายเปลี่ยนเป็นจบการศึกษา และแสดงตัวอย่างให้ตรวจแก้ก่อนยืนยัน
3. **ข้อมูลปีเก่าไม่ถูกแก้หรือลบ** หนี้ปีเก่ายังค้างอยู่และแสดงเป็น "ยอดค้างสะสมจากปีก่อน"

### 6.8 การนำเข้านักเรียน

1. รองรับ 3 ทาง:
   - ไฟล์ CSV: อ่าน UTF-8 อัตโนมัติ และถ้าเจอภาษาไทยเพี้ยน ลองอ่านแบบ Windows-874 ซึ่งเป็นรูปแบบที่ Excel ภาษาไทยมักบันทึก
   - คัดลอกตารางจาก Excel แล้ววาง
   - ไฟล์ .xlsx อ่านด้วยโค้ดของระบบเอง (ไม่ใช้ไลบรารีภายนอก)
2. ระบบอ่านไฟล์ในเบราว์เซอร์ แล้วส่งเฉพาะข้อมูลแถวไปที่ Server ไฟล์ไม่ถูกเก็บไว้ที่ใด
3. Server ตรวจทุกแถวแล้วแบ่งเป็น:
   - **ใหม่**
   - **ซ้ำ** (เลขประจำตัวตรงกับที่มีอยู่)
   - **ขัดแย้ง** (เลขเดียวกันแต่ชื่อต่างกัน)
   - **ผิดรูปแบบ** (ระบุเหตุผล)
4. ผู้ใช้เห็นตารางตัวอย่างก่อนนำเข้า แถวซ้ำกับแถวขัดแย้งต้องเลือกว่า "ข้าม" หรือ "อัปเดต" **ไม่มีการนำเข้าซ้ำโดยไม่แจ้งเตือน**

| ความเสี่ยง | มาตรการ |

| สองคนบันทึกพร้อมกัน | `LockService.getScriptLock()` ทุกงานเขียน รอ lock สูงสุดประมาณ 20 วินาที ถ้ายังไม่ได้ แจ้งว่า "ระบบกำลังบันทึกข้อมูลของผู้ใช้อื่น กรุณาลองใหม่" |
| ข้อมูลเปลี่ยนระหว่างกรอกฟอร์ม | ระบบไม่เชื่อค่าที่หน้าเว็บคำนวณมา Server อ่านข้อมูลใหม่และคำนวณใหม่ภายใต้ lock |
| กดบันทึกซ้ำ หรือเน็ตหลุดแล้วส่งใหม่ | RequestKey (idempotency) |
| เขียนสำเร็จเพียงบางส่วน (Sheets ไม่มี transaction) | ตรวจทุกเงื่อนไขก่อนเริ่มเขียน และเขียนชีตละครั้งด้วย `setValues` เรียงลำดับคงที่ ถ้าเกิดข้อผิดพลาดกลางทาง เครื่องมือ Integrity Check จะตรวจพบ |
| ทศนิยมคลาดเคลื่อน | คำนวณเป็นสตางค์ (จำนวนเต็ม) |
| วันที่เพี้ยนจากเขตเวลา | เก็บเป็นข้อความ และกำหนดเขตเวลา Asia/Bangkok ใน `appsscript.json` |

**เครื่องมือตรวจความถูกต้อง (Integrity Check)** สำหรับผู้ดูแลระบบและผู้อำนวยการ ตรวจว่า:

1. ลูกโซ่ hash ของ AuditLogs ไม่ขาด
2. ทุก Payment ที่ ACTIVE มียอดเท่ากับผลรวม Allocation และมี ReceiptEntry ที่ตรงกัน
3. ไม่มีเลขใบเสร็จซ้ำ และไม่มีเลขอยู่นอกช่วงของเล่ม
4. ไม่มีรายการเรียกเก็บที่ถูกตัดชำระเกินยอดสุทธิ
5. สถานะเล่มสอดคล้องกับจำนวนเลขที่ใช้
6. ทุกรายการการเงินมี Audit การสร้างคู่กัน

## 8. ประวัติการใช้งาน (Audit Log)

- บันทึกทุกการเพิ่ม แก้ไข ยกเลิก อนุมัติ นำเข้า สำรอง กู้คืน เข้าระบบ เข้าระบบผิด และออกจากระบบ
- ทุกแถวมีผู้ใช้ วันเวลา รายการ และค่าเดิมกับค่าใหม่ (JSON)
- ฟิลด์ลับถูกตัดออกก่อนบันทึก
- ระบบเขียน Audit ในขั้นตอนเดียวกับข้อมูลหลัก ภายใต้ lock เดียวกัน
- **Hash chain:** `Hash = SHA-256(PrevHash + เนื้อหาแถว)`
  ถ้ามีคนเปิดชีตแล้วแก้หรือลบแถว Audit โดยตรง ลูกโซ่จะขาดและ Integrity Check ตรวจพบ
- **ตำแหน่งล่าสุด (AUDIT_HEAD):** ระบบจำตำแหน่งและ hash ของแถวล่าสุดไว้ใน Script Properties ทุกครั้งที่บันทึก
  ถ้ามีคนลบแถวท้ายชีต ซึ่งลูกโซ่อย่างเดียวตรวจไม่พบ ระบบจะหาแถวนี้ไม่เจอและแจ้งเตือน
- **เขียนพร้อมข้อมูลหลักเสมอ:** ชั้นข้อมูล (`Db.gs`) บันทึก Audit ให้อัตโนมัติทุกการเพิ่มและแก้ไข โค้ดส่วนอื่นจึงลืมบันทึกไม่ได้
- **หลักฐานบนกระดาษ (แนะนำ):** รายงานประจำวันและรายงานประจำเดือนที่พิมพ์ออกมาจะมี "รหัสตรวจสอบ" (hash ล่าสุด) ท้ายกระดาษ เมื่อผู้อำนวยการลงนามแล้ว กระดาษนั้นเป็นจุดยึดที่แก้ย้อนหลังไม่ได้ ถึงผู้มีสิทธิ์เจ้าของไฟล์จะคำนวณลูกโซ่ใหม่ทั้งหมด ก็จะไม่ตรงกับกระดาษที่ลงนามแล้ว

## 10. ความปลอดภัย: มาตรการและความเสี่ยงที่ยังเหลืออยู่

### 10.1 มาตรการ

| ภัย | มาตรการ |
|---|---|
| คนนอกเข้าถึงข้อมูล | Spreadsheet ไม่แชร์ให้ใคร `doGet` ไม่ส่งข้อมูลใด ๆ ทุกข้อมูลต้องผ่าน `api` ที่ตรวจ session |
| ผู้ใช้ข้ามสิทธิ์ | ตรวจบทบาทที่ Server ทุก action (default deny) และอ่านบทบาทล่าสุดจากชีตทุกคำขอ |
| เรียกฟังก์ชันภายในจากเบราว์เซอร์ | ฟังก์ชันภายในลงท้ายด้วย `_` ฟังก์ชันติดตั้งตรวจว่าผู้รันเป็นเจ้าของ (activeUser = effectiveUser) |
| ข้อมูลนำเข้าไม่ถูกต้อง | ตรวจชนิด ความยาว ช่วงค่า และรายการค่าที่อนุญาตที่ Server ทุก field |
| XSS (ชื่อนักเรียนจากไฟล์ที่มีโค้ดแฝง) | แสดงผลด้วย `textContent` หรือ escape ทุกครั้ง ไม่ใช้ `innerHTML` กับข้อมูลผู้ใช้ |
| Formula injection ในชีต | ตั้งรูปแบบ Plain text และนำหน้าด้วย `'` |
| ข้อมูลลับรั่วไปหน้าเว็บ | ฟังก์ชันส่งออกเลือกเฉพาะ field ที่อนุญาต (allowlist) ไม่ส่งแถวดิบ |
| ข้อมูลลับใน Log | ไม่ `console.log` ข้อมูลคำขอ login ข้อผิดพลาดที่ส่งไปหน้าเว็บเป็นข้อความทั่วไป |
| Session ถูกขโมยหรือค้าง | หมดอายุเมื่อไม่ใช้งาน มีอายุสูงสุด ยกเลิกได้ทันทีด้วย SessionVersion และมีปุ่มออกจากระบบ |
| ไลบรารีภายนอกถูกแก้ไข | ไม่ใช้ไลบรารีภายนอก ชุดทดสอบตรวจว่าหน้าเว็บไม่โหลดสคริปต์จากภายนอก และติดต่อ Server ผ่าน `google.script.run` เท่านั้น |

### 10.2 ความเสี่ยงที่ระบบป้องกันได้ไม่หมด (ต้องใช้มาตรการเชิงบริหารร่วมด้วย)

1. **ผู้ที่ควบคุมบัญชีเจ้าของระบบ หรือผู้ที่ได้สิทธิ์แก้ไข Spreadsheet หรือสคริปต์ แก้ข้อมูลข้ามแอปได้**
   ระบบตรวจพบได้ด้วย hash chain, Integrity Check, ประวัติเวอร์ชัน และรหัสตรวจสอบบนรายงานที่ลงนามแล้ว แต่**ป้องกันไม่ได้ 100%**
   - ต้องจำกัดผู้ถือรหัสบัญชีเจ้าของ
   - ไม่แชร์ไฟล์
   - เปิด 2-Step Verification
2. **Google Sheets ไม่ใช่ฐานข้อมูลที่มี transaction**
   ความปลอดภัยของข้อมูลพึ่ง lock, ลำดับการเขียน และ Integrity Check
3. **ความปลอดภัยของอุปกรณ์ผู้ใช้**
   เครื่องที่มีมัลแวร์ หรือการ login บนเครื่องสาธารณะแล้วไม่ออกจากระบบ อยู่นอกการควบคุมของระบบ
4. **ข้อมูลส่วนบุคคลของนักเรียน (ผู้เยาว์)** อยู่ภายใต้ พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562
   - ระบบเก็บเท่าที่จำเป็น **ไม่เก็บเลขประจำตัวประชาชน**
   - ระยะเวลาเก็บและการแจ้งผู้ปกครอง ต้องเป็นไปตามนโยบายของโรงเรียนและต้นสังกัด
5. **ข้อมูลอยู่บนคลาวด์ของ Google**
   ต้องตรวจว่านโยบายของหน่วยงานอนุญาตให้เก็บข้อมูลการเงินและข้อมูลนักเรียนบนบัญชีประเภทที่ใช้หรือไม่ (ดูหัวข้อ 12)

## 15. การตัดสินใจ

ผู้รับผิดชอบโครงการมอบให้ผู้พัฒนาตัดสินใจแทนเจ้าหน้าที่การเงิน (21 พฤศจิกายน 2569) โดยเลือกทางที่เข้มงวดกว่าเสมอ
รายละเอียด 31 ข้อ เหตุผล และแบบตรวจยืนยันก่อนใช้งานจริง อยู่ใน [DECISIONS.md](DECISIONS.md)

ข้อที่เปลี่ยนจากค่าเริ่มต้นในร่างแรก:

- ใช้ใบเสร็จเรียงเลขที่เคร่งครัด (`RECEIPT_STRICT_SEQUENCE = TRUE`)
- การปิดเล่มก่อนใช้ครบต้องอนุมัติ (ประเภทคำขอ `BOOK_CLOSE`)
- อัตราเงินบำรุงต้องมีเลขที่หนังสือหรือมติที่อนุมัติ (`FeeSettings.ApprovalRef`)
- การลดหย่อนต้องมีเอกสารอ้างอิง (`FeeAdjustments.ReferenceDoc`)
- รายงานเลือกปีงบประมาณได้ และมีการปิดยอดประจำวัน
